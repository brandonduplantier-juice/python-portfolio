Project Write-up - In Development - E-commerce

Beauty Storefront and Merchant Platform

An online beauty store and the phone-first back office that runs it. Unlaunched, in private preview. Started November 11, 2026.

How to read the status labels

Built means the code exists. Tested locally means automated tests passed on a development machine, not on a shared build server. Checked on the private preview means it was checked on a hosted copy that the public cannot reach. Run on my own device means I ran it myself on my own hardware. Planned means designed but not built or not switched on.

What it is

An online beauty store and the back office that runs it, built as two separate applications. Shoppers can browse products, build skincare and makeup routines, and try makeup shades on a model or on their own photo in the browser. The try-on runs in the browser and the photo stays on the shopper's device.

The back office is designed for a solo seller who works only from a phone and has no technical help: products, stock, orders, suppliers, and reports, all from a phone-sized dashboard.

It is unlaunched. The store runs as a private preview that is hidden from search engines, with checkout switched off and every product marked not for sale.

Engineering problems solved

  • Found the cause of a database outage and cut the load. The free database plan hit its data-transfer limit and paused the store. I had the cause traced to one background check that read far too much data every few seconds. It went from about 986 KB per call to about 12 bytes, and usage tracking and alerts were added so it cannot happen quietly again.
  • Recovered the store from an encrypted backup at no cost. The store was restored into a new database with a scripted, step-by-step procedure and checked table by table: 72 tables and 1,178 rows. I ran that recovery myself on my own computer and it passed. The server now refuses to start on a database it cannot verify.
  • Made pages fast on free hosting that goes to sleep. Free hosting shuts down when idle and takes about 30 seconds to wake. Public pages now show a saved, checked copy of public data right away and swap in live data when the server wakes: about 1 second instead of about 30. The saved copy expires and can never make an item purchasable.
  • Fixed an intermittent test failure at its cause. A test that failed once in many runs was reproduced on demand, traced to two network answers arriving in the opposite order, and fixed. New tests were added that fail on the old code.
  • Kept backups running when the automated build service stopped. Backups run inside the application and never depended on that service, so they continued. Monitoring was moved to a free scheduler.

How the work is run

  • Every requirement has a permanent ID, a status, the evidence for that status, and what remains.
  • Work is done in numbered rounds. Each round starts with a written brief from me and ends with a written results report.
  • Every report separates what is built, what is tested, what is live on the preview, and what was physically checked. Emulated phones are never reported as real phones.
  • Changes go through branches and reviewed change requests, and I approve the merges. Anything involving money, paid services, legal text, or live selling needs my explicit approval.
  • Database changes need a verified encrypted backup and a rehearsed change first. A hard switch keeps checkout closed.

Limits

  • There are no customers, sales, or orders. The store has never been open.
  • Nothing has been tested on a physical phone or with real customer photos. Phone testing so far is emulated.
  • The accessibility result is from automated scans only (no issues found on 12 storefront pages and 20 dashboard pages). No person has checked it with a screen reader.
  • No independent security review has been done.
  • The recovery matched the backup. A comparison against the original database is still pending.
  • Automated tests have not run on the shared build server since Nov 21, 2026, so the test figures here are local runs.
  • 69 of 99 items on the original requirements list are complete.

My role and how AI was used

I am the owner and final decision maker on this project. I set the requirements, decided what to build and in what order, set the rules for testing and evidence, reviewed the results, and approved every release.

The code was written by AI coding assistants working under my direction and review. I am describing that plainly because it is how the work was done. On this project I also ran the database recovery on my own computer and wrote a fix to the start-up safety check during it.
